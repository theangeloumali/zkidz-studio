# ZKidz Studio threat model

This is the plan's §11 threat table, updated to match what shipped on `develop` (Phases 1, 2, 3, 4 and 6). Each row names
the threat, the control, the file the control lives in, and the test that proves it. Phase 7 added the tests under
`apps/server/test/security/` that drive the app as `main.ts` builds it. Each one was run with its control switched off
and failed (see "How the tests were proven" below).

Supabase (7a) and Docker (7c) are being built alongside this document. Their rows give the plan's control and list the
test as pending.

## What is being protected

- The user's footage, specs and deliverables under `ZKS_HOME`, and any files registered in place.
- The user's Claude credential: an API key in mode A, or the Claude Code login in mode T.
- The user's machine. The agent and the terminal must never become a general shell.
- The integrity of destructive and spending actions (delete, render, export). Only the user approves them.

## Trust boundaries

```ascii
 ┌──────────────── user's browser ────────────────┐       ┌───────── other sites / LAN ─────────┐
 │  app page  http://127.0.0.1:4317               │       │  attacker page, rebound DNS name,   │
 │    └─ iframe sandbox="allow-scripts"           │       │  another localhost port, LAN host   │
 │         preview  http://127.0.0.1:4318         │       └──────────────┬──────────────────────┘
 └──────────┬───────────────────────┬─────────────┘                      │ refused: Host, Sec-Fetch-Site,
            │ fetch + CSRF header   │ GET only                           │ Origin, CSRF, Content-Type, bind
            ▼                       ▼                                    ▼
 ┌──────────────────────── studio server (loopback only) ─────────────────────────────┐
 │ request guard (security/request-guards.ts) ─▶ routes ─▶ PGlite / ZKS_HOME           │
 │ preview origin (preview/preview-origin.ts): compositions only, connect-src 'none'  │
 │ agent host: canUseTool deny-by-default ─▶ studio tools ─▶ approval cards ─▶ user   │
 │ terminal (mode T): PTY runs `claude` only; hooks + MCP twin need per-session bearer │
 └────────────────────────────────────────────────────────────────────────────────────┘
            ▲ untrusted data: filenames, container tags, transcripts, agent text
```

## Accepted and residual risks

- **Local processes running as the same OS user.** Such a process can read the per-launch CSRF token from a response,
  forge `Origin`, mint a terminal ticket and drive the terminal or approve a card. The boundary against local processes
  is the loopback bind plus the OS user account, as for any local developer tool.
- **The preview origin is readable by anyone who knows a project id.** The sandboxed frame has an opaque origin, so its
  own requests arrive as `Sec-Fetch-Site: cross-site`. That makes them indistinguishable from a hostile page's, and
  neither fetch metadata nor CORP can be used on 4318. What protects it: project ids are random UUIDs, the Host
  allowlist blocks rebinding, `nosniff` stops a JSON file loading as script, and compositions hold rendered overlay
  data, not footage or credentials.
- **Injected text still reaches the model.** `read_transcript` returns the speech as JSON fields in tool output, and a
  clip reaches the agent only as a slug of its filename (`project_info`), so no planted instruction survives as
  readable text there. The plan's "delimited data block" is that JSON structure plus the edit-director skill's
  instruction to treat it as data. The hard boundary is the gate: an obedient agent can propose a destructive call,
  but only the user can let it run, and the card shows only facts the server derived.
- **Directory swap during export or a tool's file write (T-P5-R1, accepted by kai, 2026-10-24).** `deliverables.ts`
  checks that `deliverables/` is a real directory inside the project, then writes `<name>.<uuid>.part` (O_EXCL) and
  renames it; `writeProjectFile` runs `mkdir -p` before `confinePath` and opens the file O_NOFOLLOW. Node has no
  `openat`/`renameat`, so a process running as the same OS user can swap a parent directory for a symlink between the
  check and the write or rename, landing the write outside the project. Such a process can already write those
  destinations directly, and the agent has no filesystem-write, shell or symlink tool; the final component is
  protected by O_EXCL / O_NOFOLLOW, and `rename` never follows a link at its target. Revisit if jobs ever run under a
  separate OS user or Node gains `openat`/`renameat`.
